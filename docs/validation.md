# Validation

How to check that an interface, whether built by hand or generated by an AI assistant, follows the framework. Rule IDs refer to [`../DESIGN.md`](../DESIGN.md).

---

## When to validate

| Gate | When | Requirement |
| --- | --- | --- |
| Brief ready | Before building | Every line of the prototype brief is answered ([`prototyping-workflow.md`](prototyping-workflow.md#1-write-a-prototype-brief)) |
| Ready for review | Before sharing a prototype | Every applicable MUST item in the checklist below passes (PRO-7) |
| Ready to ship | Before releasing production UI | Checklist passes, the tests in "How to test" are done, and deviations are logged |

---

## Review checklist

Mark each item **Pass**, **Fail**, or **N/A**. Every item is a MUST rule unless marked *(SHOULD)*.

**Brand and tokens**
- [ ] The brand book was read; if there's none, the output says it uses fallbacks (BRD-1)
- [ ] No invented brand name, logo, colors, fonts, or voice (BRD-2)
- [ ] Brand values are applied only through tokens and never override a MUST rule (BRD-3)
- [ ] Fallbacks used are listed *(SHOULD, BRD-4)*
- [ ] Only semantic or component tokens are used; no raw values outside the token definitions (TOK-1)
- [ ] No tokens invented inside screens or components (TOK-2)

**Color**
- [ ] Text meets 4.5:1 (large text 3:1); control boundaries, focus indicators, and meaningful graphics meet 3:1 (CLR-1)
- [ ] Color is never the only way information is conveyed (CLR-2)
- [ ] Status colors are used only for their meaning (CLR-3)
- [ ] If dark mode is supported, every color has a dark value and passes CLR-1 there too (CLR-5)

**Typography**
- [ ] Sizes come from the type scale (TYP-1)
- [ ] No text smaller than 12 px (TYP-2)
- [ ] Headings are in order with one H1 per page (TYP-3)

**Layout and responsive behavior**
- [ ] Spacing comes from the spacing scale (LAY-1)
- [ ] Works at 320 px width without horizontal scrolling (RSP-1)
- [ ] Nothing essential depends on hover (RSP-2)
- [ ] Targets are at least 24 × 24 CSS px or adequately spaced (RSP-3)
- [ ] Compact density, if used, still meets target size and accessibility rules (LAY-7)
- [ ] Reading and focus order match the visual order *(SHOULD, RSP-6)*

**Components and states**
- [ ] Existing components are reused; any new component has a spec (CMP-1)
- [ ] Every applicable state from the state matrix exists (CMP-2)
- [ ] Native elements are used for buttons, links, and labels (CMP-3)
- [ ] Destructive actions ask for confirmation or offer undo (CMP-5)

**Interaction and motion**
- [ ] Every action gives visible feedback (INT-1)
- [ ] Reduced-motion preference is respected (INT-2)
- [ ] Nothing flashes more than three times per second (INT-3)
- [ ] No unexpected context change on focus or input (INT-4)

**Navigation**
- [ ] Current location is visible (NAV-1)
- [ ] Every page has a unique, descriptive title (NAV-2)
- [ ] Repeated navigation is consistent across pages (NAV-3)
- [ ] Web pages offer a way to skip repeated navigation (NAV-4)

**Content**
- [ ] Buttons and links describe their action or destination (CNT-1)
- [ ] Error messages explain what happened and how to fix it (CNT-2)
- [ ] Placeholder text is never the only label (CNT-3)

**Accessibility**
- [ ] Meets WCAG 2.2 AA or the brand book's stricter target (A11Y-1)
- [ ] Fully keyboard operable, logical order, no traps (A11Y-2)
- [ ] Focus indicator is visible, at least 2 px and 3:1, and never hidden (A11Y-3)
- [ ] Images have appropriate text alternatives (A11Y-4)
- [ ] Labels, instructions, and errors are connected to fields; status messages are announced (A11Y-5)
- [ ] Works at 200% text size and with increased text spacing (A11Y-6)
- [ ] Custom components expose name, role, and state (A11Y-7)
- [ ] Page language is set (A11Y-8)
- [ ] Dragging and multi-point gestures have a single-pointer alternative (A11Y-9)

**Prototypes**
- [ ] Labeled with fidelity and scope (PRO-1)
- [ ] Mid- and high-fidelity prototypes use tokens and documented components (PRO-2)
- [ ] At least default, empty, loading, and error states, plus success where relevant (PRO-3)
- [ ] Only fictional or anonymized content (PRO-4)
- [ ] Wireframes without brand styling are labeled as wireframes (PRO-8)

**AI-generated output**
- [ ] Token values are defined in one place (AI-2)
- [ ] No invented brand values; fallbacks are listed (AI-3)
- [ ] All applicable states are produced (AI-4)
- [ ] No check is reported as passed unless it was performed (AI-6)

After the MUST items, read through the SHOULD rules in `DESIGN.md` and record any deviation with its reason.

## How to test

| Check | Method | Example tools |
| --- | --- | --- |
| Automated scan | Run an automated accessibility checker on every screen. It finds only some issues; the manual checks are still required. | axe DevTools, Lighthouse, WAVE |
| Keyboard | Use Tab and Shift+Tab through everything; activate with Enter and Space; close overlays with Esc. Watch for visible focus, logical order, and traps. | Your keyboard |
| Screen reader | Check headings, landmarks, labels, and announcements on the main flow. | NVDA (Windows), VoiceOver (macOS, iOS), TalkBack (Android) |
| Contrast | Measure every text and background pair, plus control boundaries. | [WebAIM contrast checker](https://webaim.org/resources/contrastchecker/) |
| Zoom and reflow | Zoom to 200%; set the window to 320 px wide; increase text spacing. | Browser zoom and developer tools |
| Responsive | Check at 320, 375, 768, 1024, and 1440 px. | Browser developer tools |
| Reduced motion | Turn on the operating system's reduce-motion setting and repeat the main flow. | OS accessibility settings |

Record the method and result for each check. An item that wasn't tested is "not tested", not "pass" (AI-6).

## Scored audits

Use a scored audit to track how well a product or a set of prototypes follows the framework over time.

1. **Score** each checklist item as Pass, Fail, or N/A for the product or screen set.
2. **Rate** each failure:

   | Severity | Meaning |
   | --- | --- |
   | Critical | A failed MUST rule that blocks a task or fails an accessibility requirement |
   | Major | Any other failed MUST rule |
   | Minor | A SHOULD deviation without a documented reason |

3. **Calculate:** `compliance % = items passed ÷ items applicable × 100`, overall and for each checklist group. N/A items don't count.
4. **Block:** any open Critical item blocks release, whatever the overall score.
5. **Record** results in [`../templates/scorecard.md`](../templates/scorecard.md), and repeat on a regular cadence (for example, each release) to compare against the first, baseline audit.

Alongside compliance, it can help to track **adoption**: the share of new screens built only from documented tokens and components. High compliance with low adoption usually means the rules are being applied at audit time rather than during design.

### Reporting

A one-page summary per audit: compliance per product and the change since the last audit, the most frequent failures by rule ID, open Critical items with owners and dates, and decisions needed (exceptions or rule changes).

## Optional automation (not included)

This repository contains documentation and templates only. Teams that adopt it in a codebase often add checks such as:

- a lint rule that flags raw color or size values outside the token file (TOK-1);
- a check that every token referenced in code exists in the token file;
- automated accessibility tests in continuous integration;
- screenshot comparison to catch unintended visual changes.

These are suggestions, not features of this repository.
